## SDX M2 Release

In Secure Data Exchange (SDX) Milestone 2, teams can request API access through Common SSO, `SDX.R1.00` connections exchange tokens using the caller's approved scopes, and provider APIs receive a clear client identity on each request.

This release is published as SDX. Peer-to-peer (P2P) is another name you may hear for the same platform. The product name in this release remains Secure Data Exchange (SDX).

### Features

- **Access requests from Common SSO.** A tech lead can select SDX APIs in Common SSO and submit an access request. When the application is already an SDX subsystem, the request follows the usual connection-approval path. When it is not onboarded yet, SDX holds the request, emails the tech lead an invitation with the SDX context, and notifies APS. After onboarding, the held request is submitted for processing.
- **Connection request notifications.** The requester is notified when a connection request is approved, rejected, or revoked. The access manager is notified when a request is created or needs re-approval. Messages include the SDX and Common SSO context and a link to the SDX connections view when an action is required.
- **SDX.R1.00 authorization.** An approved `SDX.R1.00` connection is provisioned with one Common SSO integration for the subsystem and one OAuth client for the requested environment. On the consumer edge, the verified token `azp` must match that integration client, and the client must be allowed for the subsystem selected by `X-Client-Id`. Token exchange runs for every R1 connection, including connections in the same privacy zone. The provider edge checks the exchanged token. It does not perform a second exchange. `SDX.R0.00` connections keep their current behavior.
- **Token exchange scopes and audiences.** SDX requests the SDX-managed application scopes that are already in the verified caller token, plus the target provider privacy-zone scope. OpenID Connect scopes, the consumer privacy-zone scope, and client-default scopes are left out of the exchange. The caller token's `aud` claim includes the SDX token-exchange client. SDX keeps that client in the exchanged token, preserves other audiences the caller requested, and merges an optional audience configured on the connection. A provider can use that token for a later permitted exchange when it needs one.
- **Provider identity headers.** Every provider-bound request includes `X-SDX-Client-Subsystem-Id`, set by SDX from the provisioned connection. When SDX exchanges the token, the request also includes `X-SDX-Original-AZP` with the `azp` from the verified caller token. Provider APIs use these headers for client identity. The [Data Access Protocol](/reference/sdx/data-access-protocol.md) is the contract.
- **SDX gateways in the API Services Portal.** A system owner can see an SDX gateway in the Portal, including its configuration, the consumers that have access, subsystem activity, and traffic metrics.

### Enhancements

- **Routing and header contract.** The [P2P routing contract](/reference/sdx/p2p-routing-contract.md) records how a caller selects a connection and which values a provider may trust. Calling applications still use the consumer runtime host, the path `/sdx/0/{serviceId}/...`, and `X-Client-Id` set to the subsystem id. `X-Client-Id` and `X-Service-Id` select the route between the edges. They are outside the provider API contract.
- **Reference implementation.** The [SDX reference implementation](https://github.com/bcgov/sdx-reference-impl) demonstrates this flow. The sample provider validates `X-SDX-Client-Subsystem-Id`, `X-SDX-Original-AZP` when token exchange runs, and the SDX-issued token, including audience and scopes. It uses that token directly.
- **Runtime group key rotation.** Operators can publish a new edge public key, keep the previous key while in-flight signatures are still verified, and then retire the old key. The signing key id comes from the published key set. The steps, including both 300-second waits, are in [Rotate runtime group keys](/how-to/sdx-edge-runtime-groups.md#rotate-runtime-group-keys). Restart the edge with the new private key only after the new public key is in the JWKS.
- **Catalogue activity and logs.** Signed-in members can review organization activity and request logs from the SDX catalogue at [sdx.gov.bc.ca](https://sdx.gov.bc.ca).

### Fixes

- **Empty SDX gateway deletion.** Deleting an SDX gateway that has no routes, products, or deployed configuration now finishes. APS removes the namespace authorization and the namespace group. Repeating the deletion is safe. This applies to consumer and provider gateways.
- **Service environment check.** Uploading a service specification with an environment the Portal does not allow is rejected. Each APS environment publishes its own list of valid SDX environments.

### Known issues and limitations

- **Inactive connections and approved access.** Setting a connection to inactive stops requests on that connection's route. The integration's approved service list, which Common SSO and the gateway access check use, follows approval status. Deactivating a connection leaves that approval in place. Revoke the approval to remove the service from the approved access list.
- **One client per subsystem.** `SDX.R1.00` associates one Common SSO integration with a subsystem, and one OAuth client with that integration for a given environment. A subsystem with several integrations or several clients for one environment needs to be aligned to that model before R1 enforcement.
- **Caller path.** Applications call `/sdx/0/{serviceId}/...` and send `X-Client-Id`. A later pattern that selects the subsystem in the path is not part of this release.

### Upgrade and deployment

Planned production date: **Tuesday, 10 November 2026**, at **12:00 pm PCT**. The release version tag will be added when the production checklist confirms it.

APS re-provisions active `SDX.R1.00` connections during the release. `SDX.R0.00` connections stay on R0, and teams that are not using R1 keep their current configuration. An R1 caller token includes the SDX token-exchange client in `aud`. APS upgrades the runtime groups it hosts. This release does not require an edge-certificate rotation.
