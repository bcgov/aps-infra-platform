## SDX M2 Release

In Secure Data Exchange (SDX) Milestone 2, SDX exchanges tokens using the caller's approved scopes, and provider APIs can tell which client made the request.

This release is published as SDX. Peer-to-peer (P2P) is another name you may hear for the same product. The product name in this release remains Secure Data Exchange (SDX).

### Features

- **Access requests from Common SSO.** A tech lead can select the SDX APIs their application needs in Common SSO and submit an access request for approval. This becomes available after the Common SSO release that follows this SDX release.
- **Connection request notifications.** The requester is notified when a connection is approved, rejected, or revoked. The access manager is notified when a request is created or needs re-approval, with a link to the SDX connections view.
- **Tokens match the approved request.** SDX exchanges the caller token so the provider receives the scopes approved for that access.
- **Providers can identify the caller.** Each request includes `X-SDX-Client-Subsystem-Id` for the SDX client subsystem. When SDX exchanges the token, it also includes `X-SDX-Original-AZP` for the original caller. See the [Data Access Protocol](/reference/sdx/data-access-protocol.md).
- **SDX gateways in the API Services Portal.** A system owner can see an SDX gateway, the consumers that have access, and activity and traffic for the subsystem.

### Enhancements

- **Routing guidance.** The [P2P routing contract](/reference/sdx/p2p-routing-contract.md) describes how a caller reaches a provider and which values the provider can trust.
- **Reference implementation.** The [SDX reference implementation](https://github.com/bcgov/sdx-reference-impl) shows a working example of this access flow.
- **Runtime group key rotation.** Operators can rotate an edge public key while in-flight requests continue to verify. Steps are in [Rotate runtime group keys](/how-to/sdx-edge-runtime-groups.md#rotate-runtime-group-keys).
- **Catalogue activity and logs.** Signed-in members can review organization activity and request logs at [sdx.gov.bc.ca](https://sdx.gov.bc.ca).

### Fixes

- **Empty SDX gateway deletion.** An SDX gateway with no routes or products can be deleted, and deleting it again is safe.
- **Service environment check.** A service specification is rejected when its environment is not one the Portal allows.

### Known issues and limitations

- **Inactive connections.** Setting a connection to inactive stops requests on that connection. Approved access in Common SSO remains until that approval is revoked.
- **One integration per subsystem.** A subsystem uses one Common SSO integration. That same integration supports multiple environments.

### Upgrade and deployment

Planned production date: **Thursday, 12 November 2026**, at **11:00 am PCT**. The release version tag will be added when the production checklist confirms it.

APS updates active connections and the runtime groups it hosts during the release. Existing caller configuration and edge certificates stay as they are. Common SSO will not include the access-request changes on Thursday. Those become available after the Common SSO release that follows.
